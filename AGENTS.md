# my_new_ui Agent Guide

This repository contains two independent demos: a Lesson 3 controlled-generative-UI stack (Python/LangGraph backend, CopilotKit/Vite React frontend, and `L3.ipynb`) and a standalone `mcp-use` MCP Apps widget in `mcp-app/`. Run package commands from the relevant subdirectory; there is no root package manifest or shared build.

## Repository map

- `L3.ipynb`: canonical lesson flow and examples; its cells can rewrite `frontend/src/App.tsx`.
- `backend/server.py`: FastAPI/AG-UI LangGraph agent; reads `db.csv` from the repository root.
- `helper.py`: notebook lifecycle helpers for API keys, ports, server startup, and iframe display.
- `frontend/`: React 19, TypeScript, Vite 6, Tailwind CSS 4, CopilotKit, and Playwright.
- `mcp-app/`: independent Node/TypeScript MCP server and React View; server tools are in `index.ts`, UI is under `views/my-view/`.

## Dev environment

- Python 3.11+ is recommended. From the repository root:
  ```bash
  python3 -m pip install -r requirements.txt
  ```
- The lesson backend requires `GOOGLE_API_KEY`; `helper.load_api_keys()` loads it from the nearest `.env`.
- Install the lesson frontend from `frontend/` with `npm install`.
- `mcp-app/` requires Node.js `>=22.22.2`; install its locked dependencies with `npm ci`.
- The MCP widget needs no API key.

## Run the lesson stack

The canonical integrated workflow is in `L3.ipynb`, run from the repository root:

```python
from helper import load_api_keys
load_api_keys()
from backend.server import start_backend
start_backend(port=8003)
from helper import start_frontend
start_frontend(port=3003)
```

This uses frontend `3003`, CopilotKit runtime `4003`, and backend `8003`. For direct frontend development from `frontend/`:

```bash
npm run dev -- --port 3003
```

`LANGGRAPH_DEPLOYMENT_URL` overrides the runtime's default backend URL (`http://localhost:8003`).

## Build and test

From `frontend/`:

```bash
npm run build
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3003 npm run test:e2e
```

Playwright does not start the application; the backend and frontend stack must already be running. There is no frontend lint or dedicated typecheck script.

From `mcp-app/`:

```bash
npm run dev
npm run typecheck
npm run build
npm start
```

The MCP dev server defaults to `http://localhost:3000`; its endpoint is `/mcp` and Inspector is `/mcp/inspector`. There is no MCP test or lint script.

## Conventions

- Both TypeScript projects use ESM and strict TypeScript, but they are separate dependency trees: the frontend uses Zod 3 while `mcp-app` uses Zod 4.
- Frontend imports may use the `@/*` alias for `frontend/src/*`; styling is Tailwind utilities plus variables in `src/globals.css`.
- Frontend generative components export a Zod `{Component}Props` schema, infer the TypeScript props from it, and register that same schema with `useComponent()`.
- MCP tools define Zod input/output schemas, return both `content` and `structuredContent`, and declare behavioral `annotations` in `mcp-app/index.ts`.
- Under the MCP View, NodeNext relative imports include `.js` suffixes even though source files are `.tsx`.
- `mcp-app/mcp-env.d.ts` and `.mcp-use/` are generated by `mcp-use`; do not hand-edit them.

## Pitfalls

- `frontend/README (2).md` is stale: this is Vite, not Next.js, and the lesson uses ports `3003`/`4003`/`8003`, not `3000`/`8000`.
- `frontend/e2e/lesson2-frontend.spec.ts` still asserts the old Lesson 2 App Mode/todo UI and does not match the current `App.tsx`; do not treat it as a passing regression gate until updated.
- `helper.start_frontend()` and `reset_lesson()` forcibly free lesson ports; do not run them when unrelated services are using `3003`, `4003`, or `8003`.
- `query_data()` currently ignores its query argument and returns every row from `db.csv`; preserve this lesson behavior unless the task explicitly changes it.

## Graft — repo context graph

This repo is indexed in `graft/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `graft map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `graft ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `graft grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `graft skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `graft callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `graft/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `graft ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `graft build` (deterministic,
no API key, $0).
